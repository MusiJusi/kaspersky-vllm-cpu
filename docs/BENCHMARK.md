# Расширенные нагрузочные измерения

Проверяем, как параллелизм клиента влияет на задержки и пропускную способность
одного CPU-сервера. Модель и параметры сервера между сериями не меняются.

## Воспроизведение

Запустите сервис по README и откройте API в отдельном терминале:

```shell
kubectl --context kaspersky-vllm-cpu -n llm-inference port-forward service/vllm 8000:8000
```

Выполните:

```shell
python scripts/benchmark.py --requests 50 --concurrency-levels 1 2 4 --max-tokens 32 --warmup-requests 3 --ignore-eos --output results/extended/benchmark.json
```

Команда выполняет шесть серий: короткий и длинный ввод при параллелизме 1, 2
и 4. В каждой серии 3 отдельных прогревочных и 50 измеряемых запросов:
всего 300 измерений и 18 запросов прогрева. Требуется работающий сервис
и локальный файл `.local/api-token`.

Короткая проверка, используемая в CI, остаётся доступна:

```shell
python scripts/benchmark.py --requests 8 --concurrency 2 --max-tokens 32
```

Без `--ignore-eos` модель может завершить ответ раньше лимита. Старый формат
с одним уровнем параллелизма сохраняет поля `concurrency` и `cases`.
При `--concurrency-levels` результаты находятся в массиве `runs`.

## Методика

- `temperature=0`; `ignore_eos=true` обеспечивает одинаковый объём генерации:
  ровно 32 выходных токена на успешный запрос. Это контроль вычислительной
  нагрузки, а не оценка качества или естественности текста.
- Перед общей частью каждого промпта стоят идентификаторы запуска, серии
  и запроса. Прогрев использует отдельные идентификаторы. Это исключает
  полное переиспользование длинного контекста из предыдущей серии при
  включённом prefix caching. Короткий начальный префикс может совпадать.
- Число входных токенов включает шаблон чата и идентификаторы; в JSON
  сохраняются его фактические минимум, максимум и среднее для каждой серии.
- Нагрузка замкнутая: не более C одновременно выполняемых запросов, новый
  отправляется после освобождения потока. Фиксированная интенсивность
  поступления и открытая очередь клиентов не моделируются.
- TTFT измеряется от начала HTTP-вызова до первого непустого `content delta`;
  latency — до SSE-маркера `[DONE]`. Ожидание задачи в очереди клиентского
  ThreadPoolExecutor не включается; ожидание внутри сервера включается.
- Throughput считается за полное время измеряемой серии, включая запуск
  и завершение потоков, без прогрева. Выходные токены берутся из stream usage.
- p50 — медиана, p95 — nearest rank. При 50 успешных запросах p95 соответствует
  48-му значению по возрастанию, а не единственному максимуму, как при 8.
- Незавершённый SSE-поток и несовпадение фиксированной длины считаются ошибкой.
  Ошибки учитываются отдельно; при их наличии процесс завершается с кодом 1.
  Тексты ошибок HTTP, промпты, ответы и ключ доступа в отчёт не записываются.
- Завершённые серии сохраняются по мере выполнения. Полный успешный отчёт
  содержит `status=passed` и `completed_at_utc`; незавершённый — `status=running`.

## Артефакты

- [benchmark.json](../results/extended/benchmark.json) — все отдельные измерения,
  агрегаты, порядок серий, количество ошибок и параметры генерации.
- [environment.json](../results/extended/environment.json) — версия кода,
  CPU, фактические версии библиотек, аргументы сервера, ConfigMap, ресурсы
  и идентификатор образа.
- [checks.json](../results/extended/checks.json) — команда запуска, проверки API
  и приватности до и после нагрузки, неизменность конфигурации и Pod.
- [ci.json](../results/extended/ci.json) — успешный полный прогон на GitHub после
  изменения скрипта, включая совместимость короткого режима из 8 запросов.

Итоговая таблица и выводы приведены в разделе «Нагрузочные измерения» README.
Начальный прогон с 8 запросами и естественным завершением ответов сохранён
отдельно в [results/benchmark.json](../results/benchmark.json). Его абсолютные
значения не следует напрямую сопоставлять с расширенным прогоном: изменены
длина выхода и идентификаторы перед входным текстом.

## Границы выводов

Это один последовательный прогон на конкретном компьютере. Порядок уровней:
1 → 2 → 4; в каждом сначала короткий ввод, затем длинный. Перестановка порядка,
независимые повторы, доверительные интервалы и длительный тест на насыщение
не выполняются. Возможны влияние фоновой нагрузки, частот и нагрева CPU.

Клиент работает через `kubectl port-forward`, поэтому задержки включают этот
транспорт. Вход «длинный» больше короткого, но ограничен выбранным контекстом
2048 токенов; результаты не описывают модели с контекстом в десятки тысяч токенов.
По этой матрице можно выбрать полезный параллелизм для данной конфигурации,
но нельзя объявлять его универсальным оптимумом или пределом производительности.
