# Нагрузочный тест

[README](../README.md#производительность) · [Проверки](VALIDATION.md) · [Окружение](../results/extended/environment.json)

Матрица сравнивает параллелизм клиента 1, 2 и 4 на одном CPU-сервере.
Для каждого уровня используются короткий и длинный ввод: всего 6 серий,
по 3 отдельных прогрева и 50 измерений. Конфигурация сервера неизменна.

## Запуск

При работающем сервисе откройте port-forward в отдельном терминале:

```shell
kubectl --context kaspersky-vllm-cpu -n llm-inference port-forward service/vllm 8000:8000
```

Из корня проекта в Bash ([вариант для PowerShell](../README.md#производительность)):

```bash
python scripts/benchmark.py --requests 50 --concurrency-levels 1 2 4 \
    --max-tokens 32 --warmup-requests 3 --ignore-eos \
    --output results/extended/benchmark.json
```

Токен читается из `.local/api-token`. Короткий режим для CI:

```shell
python scripts/benchmark.py --requests 8 --concurrency 2 --max-tokens 32
```

## Методика

| Метрика | Определение |
| --- | --- |
| TTFT | От начала HTTP-вызова до первого непустого `content delta` |
| Latency | От начала HTTP-вызова до SSE-маркера `[DONE]` |
| Output tokens/s | Сумма выходных токенов из stream usage / время измеряемой серии |
| Requests/s | Число успешных запросов / время измеряемой серии |
| p50 / p95 | Медиана / nearest rank; для 50 запросов p95 — 48-е значение по возрастанию |

`temperature=0`, `ignore_eos=true`: каждый успешный запрос генерирует ровно 32 токена.
Фиксированный выход нужен для сравнения вычислительной нагрузки; качество текста не оценивается.
Вход содержит 84 или 918 токенов, включая шаблон чата и идентификаторы.

Идентификаторы запуска, серии и запроса стоят перед общим контекстом.
Прогрев использует отдельные идентификаторы: длинный контекст не переиспользуется целиком
из предыдущей серии при включённом prefix caching. Короткий начальный префикс может совпадать.

Нагрузка замкнутая: не более C активных запросов, следующий отправляется после освобождения потока.
Ожидание в клиентском ThreadPoolExecutor не входит в TTFT/latency; ожидание на сервере входит.
Throughput включает запуск и завершение потоков, но исключает прогрев.

Незавершённый SSE и несовпадение фиксированной длины считаются ошибкой.
Ошибки учитываются отдельно; при их наличии скрипт возвращает код 1.
Отчёт не содержит промптов, ответов, ключей и текстов ошибок HTTP.

## Выводы и параметры vLLM

Для короткого ввода переход 1 → 4 увеличил throughput в 3,62 раза,
при росте медианы полной задержки примерно на 6%. Для длинного ввода выигрыш —
2,29 раза, рост задержки — 71%. TTFT увеличился в обоих случаях.
Среди проверенных уровней 4 даёт максимальный throughput; для интерактивного
длинного ввода параллелизм 1–2 уменьшает время ожидания.

**Много коротких запросов.** Для объединения запросов в batch стоит подбирать
`max_num_seqs` и `max_num_batched_tokens` вместе с параллелизмом клиента.
Prefix caching полезен при повторяющихся префиксах. Рост параллелизма имеет смысл
до насыщения CPU и достижения допустимых задержек.

**Меньше запросов, большой контекст.** Стоит подбирать `max_num_batched_tokens`
с включённым `enable_chunked_prefill`: длинный prefill делится на части.
`max_model_len` ограничивается необходимой длиной, а `VLLM_CPU_KVCACHE_SPACE`
согласуется с контекстом, числом последовательностей и memory limit.
Потоки OpenMP и binding согласуются с выделенными CPU.

Эти параметры — направления отдельного эксперимента. В приведённой матрице
меняется только параллелизм клиента; эффект изменения серверных параметров не измерялся.

и `completed_at_utc`; незавершённый — `status=running`. Матрица записывается в `runs`,
режим с одним `--concurrency` — в `concurrency` и `cases`.

## Ограничения

Это один прогон на конкретном оборудовании. Порядок уровней 1 → 2 → 4,
в каждом сначала короткий ввод, затем длинный. Независимые повторы, доверительные
интервалы и длительная нагрузка на насыщение не выполнялись; возможны влияние
фоновой нагрузки, частот и нагрева CPU.

Задержки включают `kubectl port-forward`. Фиксированная интенсивность поступления
запросов не моделируется. Длинный ввод ограничен контекстом 2048 токенов;
выводы не распространяются на модели с контекстом в десятки тысяч токенов.

Начальный прогон из 8 запросов сохранён в [results/benchmark.json](../results/benchmark.json).
Там выход завершался по EOS, а префиксы были другими; абсолютные показатели
напрямую с расширенной матрицей не сравниваются.
